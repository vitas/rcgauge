# Target Android 16 (API 36) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** RC Throwmeter builds from a clean checkout and targets API 36, so Google Play accepts it,
while looking and measuring exactly as it does today.

**Architecture:** First restore the build: replace the dead JOML snapshot and pin `ThrowGauge`'s math
with a characterization test. Then raise the toolchain and SDK levels. Then fix the three Android 16
behavior changes in place, each driven by an instrumented test on an API 36 emulator: back
handling, system-bar insets and the large-screen orientation opt-out. The Bluetooth and sensor code
is not touched.

**Tech Stack:** Java, AGP 8.13.2, Gradle 8.14.7, JDK 17, AndroidX (appcompat, activity), data
binding, JUnit 4, Espresso 3.7.0 / androidx.test 1.7.0, Android Emulator 37.2.13 with the API 36
`google_apis` x86_64 image.

**Spec:** `docs/superpowers/specs/2026-11-16-target-api-36-design.md`

## Global Constraints

- `compileSdk 36`, `targetSdk 36`, `minSdk 21`.
- AGP `8.13.2`, Gradle `8.14.7` (`-all`, sha256 `5def2b7c967555e01ea4bbafdc829b6519edc81a4ab4ff4cccc08c1e42c4f6c0`), JDK 17.
- `org.joml:joml:1.10.9` from Maven Central, with no snapshot repositories.
- Library versions: appcompat `1.7.1`, activity `1.11.0`, material `1.13.0`, constraintlayout `2.2.1`.
  Tests: junit `4.13.2`, `androidx.test.ext:junit:1.3.0`, `androidx.test:runner:1.7.0`,
  `androidx.test:rules:1.7.0`, `androidx.test.espresso:espresso-core:3.7.0`.
- `versionCode 10`, `versionName "1.7.0"`.
- Measured angles and travel must stay identical, within 1e-8, to what JOML 1.9.3 produced.
- Bluetooth pairing and connection code (`BluetoothService`, `BluetoothPipe`, the connection parts
  of `BluetoothBaseActivity`) stays unchanged.
- Below Android 15 (API < 35) every screen must look exactly as before. The new inset code is a
  no-op there.
- Work stays on branch `target-api-36`. Commit at the end of each task (approved with this plan)
  and never push.

## Review Focus

1. A sensor mounted upside down, whose movement crosses roll ±180°, must still read 20°, not 340°.
   Test: Task 1, case `rollAcross180`.
2. The 3-button navigation bar on Android 15/16 must not cover the device list's **Select** button
   or the bottom of the settings and throw screens. Test: Task 4, run the suite in 3-button mode.
3. Back must close an open drawer, and back while the exit reminder is showing must dismiss it.
   Neither may leave the app. Tests: Task 3,
   `back_withDrawerOpen_closesDrawerAndStays` and `back_whileReminderShowing_dismissesReminderAndStays`.
4. With the system in dark mode, status bar icons must stay white over the teal strip. Test: Task 4,
   run the suite with `cmd uimode night yes`.
5. On a tablet-sized display in landscape, the app must stay portrait (letterboxed) rather than
   stretching and restarting the throw screen. Check: Task 5, step 4.

- [ ] **Step 1: Write the characterization test**

JUnit4 `@RunWith(Parameterized.class)`, one parameterized method
`resolveQuatsThrow_matchesJoml193`. Each case uses a fresh `ThrowGauge`. It calls `setIgnoreZ`,
`setThrowCalcMethod`, `SetChord(chord)`, `SetAngles(neutral)`, `SetNeutral()`, `SetAngles(current)`,
then `double travel = g.GetThrow()`. It asserts `assertEquals(expectedAngle, g.GetAngle(), 1e-8)`
and `assertEquals(expectedTravel, travel, 1e-8)`. Angles are float `{roll, pitch, yaw}` in
degrees. The test lives in package `com.pitchgauge.j9pr.pitchgauge` because
`MainPrefs.throwCalcMethodT` is package-private.

| name | neutral | current | ignoreZ | method | chord | angle | travel |
|---|---|---|---|---|---|---|---|
| pitchUp20_ortho | 0,0,0 | 0,20,0 | true | ORTHO | 50 | 19.999999999 | 17.101007166 |
| pitchDown15_ortho | 0,0,0 | 0,-15,0 | true | ORTHO | 50 | -14.999999999 | -12.940952255 |
| pitchUp20_chord | 0,0,0 | 0,20,0 | true | CHORD | 50 | 19.999999999 | 17.364817766 |
| roll10pitch30_ortho | 0,0,0 | 10,30,0 | true | ORTHO | 40 | 31.586448301 | 20.951377575 |
| yaw45_counted | 0,0,0 | 0,20,45 | false | ORTHO | 50 | 49.032470773 | 37.754063102 |
| yaw45_ignored | 0,0,0 | 0,20,45 | true | ORTHO | 50 | 19.999999999 | 17.101007166 |
| offsetNeutral_chord | 5,-3,10 | 5,25,10 | false | CHORD | 60 | 27.999999999 | 29.030627471 |
| beyond90_chord | 0,0,0 | 0,100,0 | true | CHORD | 50 | 99.999999996 | 0.0 |
| zeroChord_angleOnly | 0,0,0 | 0,35,0 | true | ORTHO | 0 | 34.999999999 | 0.0 |
| noMovement | 0,0,0 | 0,0,0 | true | ORTHO | 50 | 0.0 | 0.0 |
| rollAcross180 | -170,0,0 | 170,0,0 | true | ORTHO | 50 | 19.999999999 | 17.101007166 |

The values were recorded from JOML 1.9.3-SNAPSHOT. The 1e-9 offsets from round numbers come from
the clock-based low-pass filter's first-sample factor, which is stable to about 1e-10.

### Task 4: Screens stay clear of the system bars on Android 15/16 (edge-to-edge)

**Files:**

- Create: `app/src/androidTest/java/com/pitchgauge/j9pr/pitchgauge/SystemBarsTest.java`

**Interfaces:**
- Consumes: the permission rule pattern and the `rcgauge_api36` emulator from Task 3.
- Produces: `final class SystemBars { static void applyTo(AppCompatActivity activity) }`,

- [ ] **Step 1: Write the failing test**

Use the helper `assertClearOfSystemBars(Activity a, View topBar, View content)`, run on the main
thread. The insets come from `ViewCompat.getRootWindowInsets(decor)`, and positions come from
`getLocationOnScreen`. Assert:
- `topBar` top == `statusBars().top`
- `content` top == `topBar` bottom
- `content` bottom == `decor.getHeight() - navigationBars().bottom`
- the pixel at `(width/2, statusTop/2)` of a `decor.draw(canvas)` bitmap ==
  `ContextCompat.getColor(a, R.color.colorPrimaryDark)`
- `WindowCompat.getInsetsController(window, decor).isAppearanceLightStatusBars()` is false

The tests:
- `deviceList_staysClearOfSystemBars`: the top bar is `androidx.appcompat.R.id.action_bar_container`,
  and the content is the child of `android.R.id.content`.
- `settings_staysClearOfSystemBars`: same views, for `MainSettings`.
- `throwScreen_staysClearOfSystemBars`: same views. Launch `ThrowActivity` with
  `putParcelableArrayListExtra(BluetoothPipe.DEVICE_BT, [tag])`, where the tag has address
  `00:11:22:AA:BB:CC`, name `Test sensor` and pos `0`.
- `mainScreen_staysClearOfSystemBars`: the top bar is `R.id.toolbar`, and the content is
  `R.id.throwmeterdocscroll`.

In `@BeforeClass`, if `BluetoothAdapter.getDefaultAdapter() != null`, run
`svc bluetooth enable` through `UiAutomation.executeShellCommand` and wait for it to be enabled
(≤ 5 s). The device-list and throw tests call `assumeTrue(adapter != null)`.

- [ ] **Step 2: Run it on API 36, see it fail, and capture the "before" screenshots**

- [ ] **Step 3: Implement `SystemBars.applyTo`**

- On API < 35 (`VANILLA_ICE_CREAM`), return immediately.
- Otherwise, set the decor background to a `LayerDrawable` with two layers: the theme's window
  background, and a `colorPrimaryDark` band (gravity TOP, full width) whose height follows
  `statusBars().top`.
- Set `setAppearanceLightStatusBars(false)`.
- Pad `android.R.id.content` left, right and bottom by the `navigationBars() | displayCutout()`
  insets dispatched to it, with top 0. Use `ViewCompat.setOnApplyWindowInsetsListener` and return
  the insets unconsumed.
- If Step 2 showed the action bar or content already placed correctly, drop the matching part. The
  test's equalities decide.
